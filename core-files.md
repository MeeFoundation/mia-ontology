# Core Files

The project's core files and what each one is for — split out of [CLAUDE.md](CLAUDE.md) to keep that file smaller. The integrity checks these files are subject to live in [integrity.md](integrity.md).

| File | Purpose |
|------|---------|
| `persona.ttl` | Persona ontology — imports domain ontologies, annotates which classes/properties are required vs. optional for Mee, defines `p:Person`, the thin `hasX` link properties into the `other/` peer ontologies (`persona:hasPet`, `persona:hasVehicle`, `persona:hasIdentityDocument`, `persona:hasBankAccount` — each referenced by name with no `owl:imports` in either direction), the physical-card/wallet classes, `persona:hasSocialNetwork`, and the whole JSContact (RFC 9553) alignment layer: `p:ContactInfo` (the one template type label class this file declares — a label only, never asserted via `rdf:type`), the designator classes `persona:Credential`/`persona:WebURL`/`persona:OrganizationUnit`/`persona:JobTitle`, the annotation properties `persona:contactContext`/`persona:phoneFeature`/`persona:serviceLabel`, `persona:hasPhoto`, and `persona:Anniversary`/`persona:PersonalInfo`/`persona:PersonalityAssessment` with their own properties. Also defines `persona:specialty` (a physician's medical specialty, domain `persona:Person` directly — it describes the physician, not any appointment record — backing `cat:PrimaryCarePhysician`'s own `cell:topicGraphShape`). The rule that decides what belongs here: a property whose domain is `persona:Person` directly, an annotation property, or a thin `hasX` link into a domain modeled elsewhere; every record/document class a person merely *has*, and every property whose domain and range both sit outside `persona:Person`, lives in its own `other/*.ttl` peer ontology instead |
| `cell.ttl` | Cell ontology — `cell:Cell`, the content facet of a cell, carrying only what's common regardless of facet: `category` — range `skos:Concept`, at most one value (0..1; absent/nil exactly when the cell is of the UserDefined category, identified precisely by its cell-databook filename's `(custom)` disambiguator), else the category concept (a genuine `skos:Concept` individual scoped to `cat:CategoryScheme` — no class-value punning, since category.ttl's tree is SKOS, not OWL classes) it was originally instantiated as, fixed at creation rather than re-derived from the folder's current name, letting a recipient's app use it as a filing hint, referenced by name without `owl:imports category.ttl` (mirroring `creator`'s identical pattern below); does not contradict `cell:Cell`'s "no link to a tree position" design (see integrity.md's Check 12), since `skos:Concept` is the classificatory hierarchy — a folder is purely a filesystem concept with no RDF individual at all. The folder ownership boundary rule: a subfolder belongs to a different, nested cell rather than this one iff it directly contains a `*.databook.md` file (the only DataBook type in a user's instance tree is `cell-databook`), resolvable one folder at a time with no category-tree traversal and no dependency on any recorded path. Splits into two disjoint kinds (`owl:disjointWith` — a cell is always exactly one, never both): `cell:TemplateCell` (abstract, a reusable class-level template — carries `category` (the category concept it's a template for) and `memberGraphShape`/`topicGraphShape`, each 0..N) and `cell:MemberCell` (concrete, an actual cell instantiated in a user's own tree — carries `creator`, `owner`, and `member`). There is no `shape` property any more — a `MemberCell`'s applicable validation shape is derived, not stored: reverse-lookup the `TemplateCell` sharing the same `category` value and read whichever of its `memberGraphShape`/`topicGraphShape` values applies to the graph in question (`member` vs. `topic`) directly (the same reasoning that already removed `cell:Cell`'s own subject property). `cell:TopicCell` is a further subclass of `MemberCell`, a mixin for a cell that also carries at least one `topic` value — every real cell is typed directly `MemberCell`, optionally also `TopicCell`. `creator`'s range is a union of `p:Person`/`o:Organization`, referenced by name without importing those ontologies (mirroring `claimant`, below, though `claimant`'s own range is wider, also admitting `agent:Agent`), required exactly one value, since every actual cell's content is authored by someone. `owner` (same range as `creator` — never `agent:Agent`) identifies which of the cell's members hold the owner role rather than the regular (non-owner) member role every other member defaults to — required, one or more values, no fixed upper bound; `creator`'s own value is always included as the cell's initial owner, and any current owner may promote any other current regular member (never an agent) to owner, with no demotion modeled — see integrity.md's Check 23. `member` is an `owl:ObjectProperty` (range `cell:SCGraph`, domain `MemberCell`) — the required per-member baseline, one or more values enforced by `shacl/cell-shacl.ttl`'s `:MemberCellShape`, no fixed upper bound; `topic` (same range, domain `TopicCell`) is one or more additional graphs beyond that baseline — required (at least one) exactly when a cell is typed `TopicCell`, capped in practice at the cell's own member count (see integrity.md's Check 25), absent otherwise. `memberGraphShape`/`topicGraphShape` (domain `cell:TemplateCell`, range `sh:NodeShape`, each 0..N) link a template cell to its SHACL shape(s) describing what a `member`/`topic` graph (respectively) filed under its category should look like. Every individual in `cat-templates.ttl` is typed solely `cell:TemplateCell` — never also `cell:MemberCell` or a `cell:MemberCell`-lineage class (including `TopicCell`), since the two kinds are disjoint. Carries no link back to a folder at all — a folder is purely a filesystem concept with no RDF individual; `category` is the sole remaining record of a cell's original classification. Also defines `cell:Graph`/`cell:SCGraph` (`SCGraph` a subclass of `Graph`, no subclasses of its own — the concrete class every self-vs-other classified graph DataBook is typed as directly) and their `template`/`subject`/`claimant` annotation properties — controlled vocabularies for classifying graph files: who claimed the data (`claimant`, range a union of `p:Person`/`o:Organization`/`agent:Agent`), and what or whom the file is about (`subject` — any resource IRI; the ontology does not require it to be a person's identity, though in the example data every `subject` value happens to be a `p:Person`/`o:Organization`, a convention of the example, not an ontology requirement). The four self-vs-other combinations these two values distinguish (self-by-self, other-by-self, other-by-other, self-by-other) are derived directly from `subject`/`claimant`. A graph DataBook only ever exists to be linked from a cell (via `member`/`topic`), so its classification vocabulary lives in this same file rather than a separate one |
| `category.ttl` | Category ontology — a `skos:ConceptScheme` (`cat:CategoryScheme`), not an OWL class hierarchy: every category is a plain `skos:Concept` individual (there is no `cat:Category` class), rooted at two top concepts (`cat:Person`/`cat:Organization`, `skos:hasTopConcept`) and connected to every narrower concept via `skos:broader` (asserted child → parent, one self-contained block per concept, scoped via `skos:inScheme cat:CategoryScheme`) — a deliberate fix over an earlier `rdfs:subClassOf` design that wrongly implied OWL subsumption (`cat:Pets rdfs:subClassOf cat:Person` reads as "every Pet is a Person"; `skos:broader` carries no such entailment). No tree-position facet at all: a user's own instance-tree position is purely a filesystem fact, with `cell:category` (cell.ttl) the sole remaining RDF-level record of a cell's matched classification. No `cat:templateCell` property (removed) — a templated category's reusable content is found via `cat-templates.ttl`'s own `cell:TemplateCell` individuals, each carrying its own `cell:category` value naming the concept it's a template for, a reverse lookup rather than a forward pointer. Carries no `owl:imports` at all any more, since nothing in it references a `cell:` term |
| `cat-templates.ttl` | Class-level `cell:Cell` templates, 102 in total — one individual per category concept in `category.ttl` except the two SKOS top concepts `cat:Person`/`cat:Organization` themselves (see integrity.md's Check 29 — no real leaf cell is ever instantiated as bare "Person" or "Organization"), each carrying its own `cell:category` value naming that concept — the reverse of the deleted `category.ttl`'s `cat:templateCell` forward-pointer — plus one more, `ctpl:UserDefinedTemplateCell`, with **no** `cell:category` value at all: the fallback template for a cell created with no category selected (the Custom/UserDefined case), found as the unique category-less `cell:TemplateCell` rather than by the usual reverse lookup. Each is typed solely `cell:Cell, cell:TemplateCell` — `cell:TemplateCell` and `cell:MemberCell` are disjoint, so a template cell carries no member composition of its own, just its shape property/properties pointing to SHACL shape(s) — in `shacl/persona-shacl.ttl`/`shacl/contactinfo-shacl.ttl` for a template targeting a `persona:`-defined class, otherwise in the `other/shacl/<name>-shacl.ttl` file paired with whichever `other/*.ttl` peer ontology declares that template label class (`petshapes:`, `vehicleshapes:`, `idocshapes:`, `mashapes:`, `sashapes:`, `bankingshapes:`, `residenceshapes:`, `itineraryshapes:`) — following two patterns (a third, member-only document shape with no topic content at all, existed before this file's Passport/BirthCertificate/DriversLicense templates were each flipped to the topic-based pattern below, and is now empty): (1) `cell:memberGraphShape pshapes:ContactInfoShape` plus `cell:topicGraphShape` carrying the category's own record shape, `cell:isTopicCell true` — the 15 whose real content is filed as a `cell:topic` graph instead (Passport, SSN, BirthCertificate, DriversLicense, MedicalAppointment, PetMedications, PetProfile, VehicleProfile, Companies, BankingPayments, Home, Trips — each a real reified document/account type — plus HealthWellness, PrimaryCarePhysician, and PetsCareAndFeeding, each a more modest shape with every property optional, per integrity.md's Check 32) — `cat:BankingPayments` carries three `cell:topicGraphShape` values at once (`ServiceAccountShape`, `DebitCardShape`, `CheckingAccountShape`), since a single Citibank-claimed topic graph there holds all three templates' content together — `cat:PrimaryCarePhysician` similarly carries two (`PrimaryCarePhysicianShape`, `ContactInfoShape`), since Dr. Jane Starostina's own topic graph (graph-25) doubles as both her optional specialty record and a business-card profile; (2) `cell:memberGraphShape pshapes:ContactInfoShape` alone, no `cell:topicGraphShape`, `cell:isTopicCell false` — every other templated category (86 of them, including `cat:People` and three of its four direct `skos:broader` children, `cat:Affiliations`, and every other category with no document type or topic content of its own), plus `ctpl:UserDefinedTemplateCell`; and (3) `cell:memberGraphShape pshapes:ContactInfoShape` plus a `cell:topicGraphShape`, but `cell:isTopicCell false` — a category that expects no topic at instantiation yet names the shape the app offers first should the user manually add one anyway — a hint, not a restriction, since a manually-added topic may carry any shape the user picks (`cat:ImmediateFamily` alone today, carrying `cell:topicGraphShape pshapes:ContactInfoShape` for the Contact Info topic in cell-12; see integrity.md's Check 31). **`cell:memberGraphShape pshapes:ContactInfoShape` is asserted directly and identically on every one of the 102 individuals with no exception** (integrity.md's Check 30) — not hoisted onto the `cell:TemplateCell` class itself via an OWL restriction, since nothing in this project's validation pipeline runs a reasoner to materialize such an entailment. The required `cell:isTopicCell` — `true` on the 16 pattern-(1) templates, `false` on the other 86 (pattern (2), including `ctpl:UserDefinedTemplateCell`) — flags whether Lazy Instantiation's clone of the template is expected to be typed `cell:TopicCell` (see integrity.md's Check 31 — an `isTopicCell true` category's real cells must always carry a `topic`, while any `cell:MemberCell` may gain up to one manually-added `topic` regardless of its template's flag — and integrity.md's Check 32 — `isTopicCell true` always requires a real `cell:topicGraphShape`, so there is no state where a template is `isTopicCell true` with no shape at all). Imports `cell.ttl` directly — no mutual import with `category.ttl` |
| `shacl/cell-shacl.ttl` | SHACL validation shapes for `cell:Cell` DataBook instances, split across shapes matching `cell.ttl`'s two-kind split: `:CellShape` (target `cell:Cell`) — `category` cardinality (at most one — 0..1 — constrained via `sh:class skos:Concept` plus a nested `skos:inScheme cat:CategoryScheme` check, now that category.ttl's tree is genuine SKOS individuals rather than class-value-punned classes), plus an `sh:xone` requiring `rdf:type` to be exactly one of `cell:TemplateCell`/`cell:MemberCell` (mirroring `cell.ttl`'s `owl:disjointWith`); `:TemplateCellShape` (target `cell:TemplateCell`) — `memberGraphShape`/`topicGraphShape` cardinality (zero or more values each, no fixed upper bound; deliberately not constrained to `sh:class sh:NodeShape` since their values are only typed as such in the per-template `*-shacl.ttl` files, which the cell pass excludes from its shapes) and `isTopicCell` cardinality (required, exactly one value, must be a boolean); `:MemberCellShape` (target `cell:MemberCell`) — `creator` (required, exactly one value) constrained to be a `p:Person` or `o:Organization`, `owner` (required, one or more values, no fixed upper bound, each constrained to be a `p:Person` or `o:Organization`, never an `agent:Agent`), `member` (required, one or more values, no fixed upper bound, each constrained to `cell:SCGraph`). There is no `shape` shape any more — a `MemberCell`'s validation shape is derived via its own `category` value, never stored, so there's nothing to constrain; there is likewise no SHACL constraint tying `owner` to `creator`/`member` — that invariant is checked only by integrity.md's Check 23; `:TopicCellShape` (target `cell:TopicCell`, the mixin subclass for a cell that carries at least one `topic` value) — `topic` required, at least one value (SHACL sets no maximum here; the real cap — one value per cell member, each with a distinct claimant — is integrity.md's Check 25, not a SHACL constraint), each constrained to be a `cell:SCGraph`. There is no cell-level subject property/shape at all — a cell's own subject is derived, never stored (see integrity.md's Check 18); `:SCGraphShape` (target `cell:SCGraph`) constrains that different, graph-level `subject`/`claimant` instead — `claimant` required exactly once and constrained to a `p:Person`/`o:Organization`/`agent:Agent`, `subject` required exactly once and constrained to be an IRI — its range is `xsd:anyURI`, so a graph's subject need not be a person's identity. A graph DataBook does not carry `cell:creator` (or any creator property) — that stays a `cell:Cell`-only property |
| `shacl/persona-shacl.ttl` | SHACL validation shapes — constraint rules for all `persona:Person` instances (SSN format, address cardinality, payment cards, wallet, social network, etc.), plus `:SSNShape`, `:HealthWellnessShape`, and `:PrimaryCarePhysicianShape` (`cat:PrimaryCarePhysician`'s own `cell:topicGraphShape`, targeting `persona:Person` directly since a physician has no reified document individual of their own; its one optional property is `persona:specialty`). The `:DebitCardShape`/`:CheckingAccountShape` live in `other/shacl/banking-shacl.ttl` instead, paired with `other/banking.ttl` |
| `other/medical-appointments.ttl` | A small `other/` peer ontology — the claims two people share to arrange a medical appointment on someone else's behalf. Defines `medicalappointments:MedicalAppointmentRecord` (an independent template type label class, also the `rdf:type` of the reified record individual) plus its own claim properties (`forPatient`, `hasPrimaryCarePhysician`, `currentMedication`, `allergy`, `medicalHistoryNote`, `insuranceProvider`, `insurancePolicyNumber`, `insuranceGroupNumber`, `preferredPharmacy`), all domain `MedicalAppointmentRecord`. `persona.ttl` carries no thin `hasX` link into it — a record here is shared between the two coordinating members rather than possessed by one `persona:Person`. Doc alias: `ma:`. Carries no `owl:imports` |
| `other/shacl/medical-appointments-shacl.ttl` | `:MedicalAppointmentRecordShape`, linked from `cat:MedicalAppointment`'s template cell via `cell:topicGraphShape`; run against the individual graph file, not merged data |
| `other/service-accounts.ttl` | A small `other/` peer ontology — an online service account a person holds (Google, AT&T, a bank's web portal). Defines `serviceaccounts:ServiceAccount` (always multi-typed `cco:ent00000033` Online Service Account, so service name/username/service URI reuse that class's own properties directly) and `serviceaccounts:hasPassword` (domain `cco:ent00000033` — internal to this domain, not a `persona:Person` property). `persona.ttl` carries no thin `hasX` link into it: CCO's own `holds user account` (`cco:ent00000045`) already plays that role. Doc alias: `sa:`. Carries no `owl:imports` |
| `other/shacl/service-accounts-shacl.ttl` | `:ServiceAccountShape`, linked from `cat:Companies`'s and `cat:BankingPayments`'s template cells via `cell:topicGraphShape`; run against the individual graph file, not merged data |
| `other/banking.ttl` | A small `other/` peer ontology — a debit card and the checking account it draws on. Defines `banking:DebitCard` (always multi-typed `cco:ent00000051`), `banking:CheckingAccount`, and `banking:accessesBankAccount` (domain `cco:ent00000051`, range `banking:CheckingAccount` — internal plumbing between two classes in this same file, which is why it isn't in `persona.ttl`). `persona:hasBankAccount` (domain `persona:Person`, range `banking:CheckingAccount`) stays in `persona.ttl` as the thin link. Carries no `owl:imports` |
| `other/shacl/banking-shacl.ttl` | `:DebitCardShape` (targets `cco:ent00000051` directly, since every `banking:DebitCard` individual is multi-typed alongside it) and `:CheckingAccountShape` (targets `banking:CheckingAccount`), both linked from `cat:BankingPayments`'s template cell via `cell:topicGraphShape`; run against the individual graph file, not merged data |
| `other/residences.ttl` | A small `other/` peer ontology — a place a person has lived, current or past. Defines `residences:Residence` (always multi-typed `cco:ent00000016` AddressDesignation, so its address/participant/temporal-region properties reuse that class's own pattern directly), and nothing else. `persona.ttl` carries no thin `hasX` link into it — a residence is simply the `cell:topic` of its own `cat:Home` cell. Carries no `owl:imports` |
| `other/shacl/residences-shacl.ttl` | `:ResidenceShape`, linked from `cat:Home`'s template cell via `cell:topicGraphShape`; run against the individual graph file, not merged data |
| `other/itineraries.ttl` | A small `other/` peer ontology — a specific trip a person is planning or taking, as distinct from `cat:Travel`'s broader loyalty-program information. Defines `itineraries:Itinerary`, alone among this project's template label classes in being multi-typed alongside nothing (no domain ontology models trip-planning data yet) and carrying no structured properties of its own beyond a human-readable `rdfs:label`/`rdfs:comment`. `persona.ttl` carries no thin `hasX` link into it. Carries no `owl:imports` |
| `other/shacl/itineraries-shacl.ttl` | `:ItineraryShape`, linked from `cat:Trips`'s template cell via `cell:topicGraphShape`; run against the individual graph file, not merged data |
| `other/pets.ttl` | The first `other/` peer ontology — pet domain-modeling kept out of `persona.ttl` (see Project Overview). Defines `pets:Pet` (template label + the pet individual's own `rdf:type`, carrying required `pets:name` (`xsd:string`) and `pets:hasSpecies` (an NCBITaxon class IRI), and optional `pets:hasBreed` (a VBO class IRI, including VBO's own "Mixed Breed" classes), `pets:birthDate` (`xsd:date` or `xsd:gYear` — exact or approximate), `pets:hasBodyWeight`/`pets:BodyWeight` (mirrors `pets:DosageAmount`'s CCO Measurement-Unit/Information-Bearing-Entity reification, but with a required rather than optional unit), `pets:sex` (`"Male"`/`"Female"`), and `pets:isSpayedOrNeutered` (`xsd:boolean`)) and `pets:PetMedicationRecord`/`pets:Medication` (`pets:hasMedication`, `pets:hasActiveIngredient` (ChEBI class IRIs), `pets:hasDoseForm` (DrOn dose-form class IRIs), `pets:DosageAmount`/`pets:hasDosageAmount` (CCO Measurement-Unit/Information-Bearing-Entity machinery), `pets:MedicationAdministration`/`pets:hasAdministration` (DrOn drug-administration process + BFO TemporalInterval), `pets:medicationFrequencyPerDay`, `pets:medicationBrandName`, `pets:medicationManufacturer`, `pets:medicationDuration`). Both are independent template type label classes, targeted directly by their own SHACL shape (`other/shacl/pets-shacl.ttl`). `owl:imports` `project_files/dron-upper.ttl`, `project_files/ncbitaxon-subset.ttl`, and `project_files/vbo-subset.ttl` |
| `other/shacl/pets-shacl.ttl` | SHACL shapes for `pets:Pet` (`:PetShape`) and `pets:PetMedicationRecord`/`pets:Medication` (`:PetMedicationRecordShape`, `:MedicationShape`, `:DosageAmountShape`, `:MedicationAdministrationShape`), each linked from its `cat-templates.ttl` template cell via `cell:topicGraphShape`; run against the individual graph file, not merged data |
| `project_files/dron-upper.ttl` | A hand-curated subset of DrOn (the Drug Ontology)'s upper module — five classes ("drug product", "active ingredient", "drug tablet", "drug capsule", "drug administration") cited by their real upstream IRIs, not a full mirror (DrOn's full distribution is ~300MB of RxNorm-derived per-product classes not relevant here). `owl:import`ed by `other/pets.ttl`. The first non-CCO/non-`mee.foundation` external ontology this project has ever vendored |
| `project_files/ncbitaxon-subset.ttl` | A hand-curated subset of NCBI Taxonomy (NCBITaxon) — 33 common pet species across mammals, birds, reptiles/amphibians, and aquarium fish, cited by their real upstream IRIs, not a full mirror (NCBITaxon's full distribution is ~2.7 million classes covering all of life, so a full extraction — unlike `vbo-subset.ttl`'s — was never on the table). `owl:import`ed by `other/pets.ttl` |
| `project_files/vbo-subset.ttl` | A real, filtered *extraction* of VBO (the Vertebrate Breed Ontology) — every one of the 2,822 real breed classes (plus each species' own top-level breed-group node) under the 9 companion-pet species this project names, preserving VBO's own `subClassOf` breed tree (species-group → breed → sub-breed/variety); not hand-picked, not a full mirror either — VBO's real full release (19,961 classes, ~78% livestock/poultry/game breeds with no place in a *Pets* ontology) was small enough to extract in full for its pet-relevant slice, unlike NCBITaxon's true scale. CC-BY 4.0 (unlike NCBITaxon/DrOn's CC0/public-domain status) — attribution given in the file's own header and per-class comments. `owl:import`ed by `other/pets.ttl` |
| `other/vehicles.ttl` | The second `other/` peer ontology — vehicle domain-modeling, mirroring `other/pets.ttl`'s own pattern (see Project Overview). An independent template type label class, targeted directly by its own SHACL shape (`other/shacl/vehicles-shacl.ttl`). `owl:imports` `project_files/wikidata-vehicle-makes-subset.ttl` and `project_files/wikidata-vehicle-models-subset.ttl` |
| `other/shacl/vehicles-shacl.ttl` | SHACL shapes for `vehicles:Vehicle` (`:VehicleShape`), `vehicles:OdometerReading` (`:OdometerReadingShape`), and `vehicles:EngineSpecification` (`:EngineSpecificationShape`); run against the individual graph file, not merged data |
| `other/identity-documents.ttl` | The third `other/` peer ontology — government-issued identity document classes kept out of `persona.ttl` (see Project Overview). | `shacl/contactinfo-shacl.ttl` | Per-template SHACL shapes for ContactInfo graph files — run against the individual graph file, not merged data (ContactInfo is reused across many unrelated tree positions with no single category concept of its own, so its shape stays standalone) |
| `helpers/validate.py` | The project's SHACL validation, run as `python3 helpers/validate.py` from the repo root. Walks every cell-databook under `example/Cells/` and validates each cell in isolation from every other cell, in two passes: a **cell pass** (the cell's whole content — all its graphs' Turtle plus its own synthesized `cell:` triples — against `shacl/cell-shacl.ttl`, `shacl/persona-shacl.ttl`, `shacl/organization-shacl.ttl` and `shacl/agent-shacl.ttl`) and a **template pass** (each graph carrying a `template:` value, on its own, against the shape that value names). The two passes use different base merges — `cat-templates.ttl` is in the template pass's, deliberately out of the cell pass's. Exits non-zero on any violation, so it doubles as a CI-style gate. See integrity.md's Check 5 |
| `helpers/extract-all.py` | Concatenates every embedded graph's fenced Turtle block across every cell-databook under a root (skipping `under-development/`), stripping each fence's own `<!-- databook: -->` marker lines. Not part of validation — it produces the merged whole-tree dump for the questions that genuinely need the union (integrity.md's Check 4's cross-cell reachability; loading the example into a triplestore), documented under EXAMPLE.md's "Merged whole-tree dump". Shares `databook_graphs.iter_graph_blocks()` with `helpers/extract-graph.py` and `helpers/validate.py` |
| `helpers/yaml-to-rdf.py` | Synthesizes `cell:` triples from each cell-databook's `mia.` YAML frontmatter (including each `mia.member`/`mia.topic` entry's own embedded `id`/`claimant`/`subject`/`template` fields), the whole-tree half of the synthesis `helpers/validate.py`'s cell pass does one cell at a time; both call `databook_graphs.process_cell_databook()`. Turtle-block extraction alone would never surface these, since cell-databooks mostly carry no fenced Turtle of their own, so without this synthesis `cell:Cell` individuals and `cell:SCGraph`'s subject/claimant/template never reach RDF at all. No category-side synthesis at all — a folder's tree position is purely a filesystem fact with no RDF individual to synthesize |
| `project_files/` | Reference materials: imported domain ontologies (PersonOntology.ttl, AddressOntology.ttl, StagingOntology.ttl), BFO/CCO source files, PDFs, docs, plus the hand-curated vendor subsets (`dron-upper.ttl`, `ncbitaxon-subset.ttl`, `vbo-subset.ttl`) `owl:import`ed by `other/pets.ttl`, (`wikidata-vehicle-makes-subset.ttl`, `wikidata-vehicle-models-subset.ttl`) `owl:import`ed by `other/vehicles.ttl`, and `prov-upper.ttl` (a hand-curated W3C PROV-O subset — `prov:Agent`/`prov:SoftwareAgent`/`prov:Person`/`prov:Organization`/`prov:actedOnBehalfOf`) `owl:import`ed by `agent.ttl` |
| `APP-BEHAVIOR.md` | App-behavior documentation — how the app uses the ontologies above: cell lifecycle (Lazy Instantiation), storage and sync, sharing/permissions (Number of Members, Permissions), cell naming/renaming/collision handling, how a cell is persisted as a filesystem folder (naming and fill/text-color conventions), and the auto-filing heuristic used when a shared cell is received. Not itself an RDF file — no `owl:versionInfo`. Linked from `README.md` and `EXAMPLE.md` |
